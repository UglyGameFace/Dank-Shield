# Phase 16: preserve the original Dank Shield activity feed exactly

**Source:** original live shared Supabase `hyncpbvqyjojxhjzcdzg`.
**Target:** OFFLINE dedicated Supabase `viamriafkbqhquvrsnua`, production remains on source.

Verified 2026-10-20 source data: `activity_feed_events` has **4,756 UUID-unique records**, all owned by nine known guilds (dedicated database has corresponding guild configs). The 25 table columns and UUID primary key match the dedicated table. Original payload totals approximately **52 MB**, with largest record **45,228 bytes**. Links: 3,369 feed entries link to the 3,369 exact staff-action rows now verified in the dedicated candidate, and 632 link to preserved `member_events`; no dangling references on original source. The feed's last event was October 18, but it is essential historical moderation/member activity, not a queue of pending Discord mutations.

**Critical source trigger parity:** Original database defines `sync_activity_feed_meta_columns()`, fired BEFORE INSERT/UPDATE. It normalizes `meta` and `metadata` to the canonical metadata value, and makes `search_text` non-null. The dedicated database had this trigger missing. The source history includes **1,825 original rows where `meta` differs from `metadata`**, so a naive bulk insert with the new trigger enabled would silently rewrite evidence. The dedicated migration `202610200025_dankshield_activity_feed_source_trigger.sql` restores the original function's runtime semantics for future events; the import workflow temporarily disables only this trigger INSIDE the single destination transaction and re-enables it before commit, preserving historical fields unchanged.

**Manual, owner-only workflow** `.github/workflows/dankshield-activity-feed-transfer.yml` after merge supports `preview` and separately confirmed `stage` only on exact `main`. Uses existing `DANK_SOURCE_DATABASE_URL` and `DANK_FRESH_DATABASE_URL` GitHub Actions secrets. Stage requires `COPY_DANKSHIELD_ACTIVITY_FEED_OFFLINE_ONLY`. The source PostgreSQL connection is read-only, repeatable-read. The empty offline destination is validated for source-exact schema, service-only RLS/grants and enabled trigger. Max 8,000 rows, 100MB original, 128KB per row; 100-row pages of source `to_jsonb(row)::text`, never JS numeric conversion. Each copied page is verified with full JSONB equality before commit; a final whole-history PostgreSQL digest and metadata-difference count are verified before the single target commit. Recheck any source writes before final cutover.

CI uses an isolated PostgreSQL 16 database fixture with NO production credentials to prove runtime normalization of new events and exact preservation of old divergent history with the trigger disabled and re-enabled within rollback-only SQL tests.

**No source deletion, no Discord messages or new moderation activity, no old terminal job replay, no Discloud credential updates, no production cutover.** Original external invite events are intentionally excluded per owner's data-minimization preference. Old automatically generated configuration revisions need not be blindly migrated. Audit_events/audit_logs in old shared project have unproven app ownership and should not be imported indiscriminately.

After this slice: production cutover still requires complete final source delta, independent encrypted database backup + off-host restore, Discord service canary and validated rollback. It is unsafe to claim 100% until those are proven.
